# Windows Cua carrier

The daemon serves `rdpilot-bridge.exe`, the Cua archive and `manifest.json` on `\\tsclient\RDPILOT\bundle`. Windows asks for confirmation before it starts a program from the redirected drive, so the daemon's Run dialog line (`cmd /d /c ...`) copies the served bridge to `%LOCALAPPDATA%\rdpilot\launch-<generation>.exe`, starts that copy with `install`, and deletes it when it exits. The bridge has three subcommands:

- `install --generation N [--source DIR]` reads the manifest from the served directory (default `\\tsclient\RDPILOT\bundle`), checks that its own image is the bridge the manifest names, copies and verifies the bridge and the archive, extracts the archive into `%LOCALAPPDATA%\rdpilot\.staging-*`, verifies every extracted file, and publishes `%LOCALAPPDATA%\rdpilot\<bundle id>` with one rename. A verified existing installation is reused. It then starts the installed copy with `run` and exits.
- `run --generation N` holds the `Local\rdpilot-cua-<generation>` mutex (a repeated launch for the same generation exits quietly), opens `RDPILOT_CUA_V1` in its interactive RDP session, and starts only the adjacent `cua-driver.exe mcp --direct`, with telemetry disabled. Hello must name the bundle id of the adjacent manifest; Ready reports the bridge version.
- `cleanup` stops this user's processes under `%LOCALAPPDATA%\rdpilot` in the current session and removes `%LOCALAPPDATA%\rdpilot` and `%TEMP%\rdpilot-transfer-root`. Run from inside the installation, it removes everything else at once and leaves a detached `cmd` that deletes the rest after it exits.

The bridge writes nothing outside those two directories: no registry, service, scheduled task, PATH or firewall change. `tests/guest_footprint.rs` checks its source for such APIs.

The protocol crate owns a versioned JSON envelope inside a little-endian u32 length frame. Inner MCP JSON values are opaque; carrier control IDs and Cua request IDs are unrelated. One attachment is permitted per bridge. Attachment IDs must increase within the bridge generation, including after failed starts; delayed closes therefore cannot close a new runtime. A new attachment always creates a new contained process and MCP session. Nothing is replayed.

The Windows process is created suspended, assigned to a kill-on-close job, then resumed. Failure to establish containment fails the attachment. Dropping an attachment kills the tree. The WTS adapter queries its underlying file handle for separate overlapped read and write operations; WTSVirtualChannelRead/Write themselves are not thread safe. Reads validate documented CHANNEL_PDU_HEADER length and FIRST/LAST sequencing before passing bytes to the independent application frame decoder. Writes use 1600-byte chunks and require the exact reported byte count. A short write fails the carrier instead of replaying a possibly committed request. Cancellation completion races retain the received bytes.

Limits are implementation constants: 16 MiB outer frame, 32 queued frames, 256 pending RPC requests, 8 KiB drained stderr tail, 30-second RPC/transfer deadline, 5-second pipe/frame-write deadline, 3-second child teardown and 45-second carrier inactivity timeout. Requests queued behind a stuck tool retain their original admission time. Pending RPC IDs include direction and JSON type. Stderr never reaches MCP stdout. Saturation closes the affected attachment, or the carrier if its output itself is saturated. A transfer deadline exits the carrier; process shutdown bounds an unresponsive remote filesystem. The SDK must send periodic Ping when idle.

Transfers use `%TEMP%\rdpilot-transfer-root` and `\\tsclient\RDPILOT`, with relative names only. Both sides reject traversal, ADS, Windows special aliases and existing reparse-point ancestors. New destination creation is atomic and never clobbers a file. A cancelled/failed copy removes its own partial destination; hashing is incremental. Callers must stage downloads at an unused name. These checks are not a security boundary against another process under the same Windows identity racing filesystem mutations.

`cargo test -p rdpilot-bridge -p rdpilot-bridge-protocol` covers bounded codec parsing, real fake-child streams on Unix, timeout/control independence, process-group cleanup, concurrent target streams and transfer semantics. Windows library tests additionally exercise suspended launch/job containment with a PowerShell descendant. The actual WTS header behavior, upstream Cua executable and independent Windows session isolation still require the focused live integration harness.
