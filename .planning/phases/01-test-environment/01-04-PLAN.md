  <decision>Where does the Automation Account that deletes the test resource group live, and at what scope does its managed identity get RBAC?</decision>
  <context>
    RESEARCH.md Pitfall 4 / Open Q2 / Assumption A5: a runbook can delete the RG it lives in, but the job host (the Automation Account) is destroyed mid-delete, so the final job status may not report success. The cleaner alternative is a separate persistent "management" RG/Automation Account that outlives its target. This choice drives the RBAC scope and where the auto-destroy resources are declared. The planner must NOT silently pick one (PATTERNS.md Open Decision 1).
  </context>
  <action>
    Present the two topology options below to the user along with their RBAC-scope and job-status tradeoffs, and confirm the West Europe default region + target subscription (RESEARCH.md A6). Record the selection so Task 2 implements exactly that topology and RBAC scope. Do not proceed to Task 2 until the user selects.
  </action>
  <options>
    <option id="self-contained">
      <name>Automation Account inside the disposable test RG</name>
      <pros>Single RG; everything torn down together; simplest Bicep; matches "one main.bicep, one RG" convention.</pros>
      <cons>Self-delete is messy — the job host vanishes mid-delete so the final runbook job status may not report; identity must be scoped at subscription (or parent) level to delete its own RG cleanly, which is broader than RG-Contributor.</cons>
    </option>
    <option id="separate-management">
      <name>Separate persistent management RG + Automation Account</name>
      <pros>Deleter outlives its target; clean job status; identity needs only Contributor over the TEST RG (tightest least-privilege).</pros>
      <cons>Requires a persistent management RG that is NOT torn down by `down`; slightly more setup; two RGs to reason about.</cons>
    </option>
  </options>

  <done>The auto-destroy topology and the runbook-identity RBAC scope are selected and recorded; region + subscription confirmed.</done>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| runbook managed identity → ARM (delete) | An automated identity holds rights to delete a resource group |
| manage-env.ps1 → .secrets/connection.json | The generated admin password is written to disk |
| dev machine → ipify (HTTPS) | The dev's public IP is fetched from an external service |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-01-11 | Elevation of Privilege | Over-privileged runbook identity | mitigate | Role assignment grants Contributor scoped per topology (RG for separate-management; subscription only if self-delete requires it) — never subscription-Owner; build gate rejects `Owner`. ASVS V4. HIGH — blocks if Owner granted. |
| T-01-12 | Information Disclosure | Generated password leaked (console/log/git) | mitigate | Password via crypto RNG, never echoed, written only to gitignored `.secrets/connection.json`; passed to ARM as `@secure()`; `.gitignore` from Plan 01. ASVS V7. HIGH — blocks if password is echoed or written outside `.secrets/`. |
| T-01-13 | Denial of Service (financial) | Forgotten box / runaway cost | mitigate | Scheduled auto-destroy runbook (ENV-03) + on-demand `down`; auto-destroy fires even if dev machine is off (D-04). |
| T-01-14 | Spoofing | ipify returns wrong/spoofed IP → NSG opens to wrong source | mitigate | `-AllowedSourceIp` override validated as IPv4; HTTPS to ipify; NSG still scoped to a single IP (not 0.0.0.0/0). ASVS V5. |
| T-01-15 | Repudiation | Self-delete job status not reported | accept | Documented caveat for the `self-contained` topology (Pitfall 4); separate-management topology avoids it. |
</threat_model>
