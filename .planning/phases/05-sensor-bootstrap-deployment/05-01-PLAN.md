Create `sensor/Envelope.cs` mirroring the Rust wire shape exactly (RESEARCH Code Examples): a record/type with `version` (uint), `req_id` (ulong), `type` (string serialized as the bare values "Version"/"Ping"/"Pong"), and a nullable `payload`. Create `sensor/EnvelopeJsonContext.cs` with `[JsonSerializable(typeof(Envelope))]` on a `partial class EnvelopeJsonContext : JsonSerializerContext` (AOT-safe path — never the reflection-based `JsonSerializer.Serialize<Envelope>` overload, RESEARCH Anti-Patterns).

Create `sensor/Program.cs` implementing, in order:
1. An internal `Wts` P/Invoke surface using `[LibraryImport("wtsapi32.dll", ...)]` (NOT `[DllImport]` — AOT-incompatible for the string-marshalled open call, RESEARCH Pitfall 1). Declare `WTSVirtualChannelOpenEx(uint, string, uint)` with explicit `StringMarshalling`, plus `WTSVirtualChannelRead`/`WTSVirtualChannelWrite`/`WTSVirtualChannelClose` (blittable). Constants `WTS_CURRENT_SESSION = 0xFFFFFFFF`, `WTS_CHANNEL_OPTION_DYNAMIC = 0x1`. Per RESEARCH Open Question #3 / Assumption A3: try `StringMarshalling.Utf16` first; if the open call returns an entry-point/marshalling failure, flip to `StringMarshalling.Custom`/ANSI to match the ANSI `A` entry point the Phase-4 fixture used — this is a cheap runtime confirmation, not a structural risk.
2. Open `RDPILOT_SENSOR` in a bounded retry-poll loop (~20 attempts, 500 ms apart) that tolerates the ERROR_GEN_FAILURE/0x31 timing race (D-5.7 constraint #1); on total failure exit non-zero with a diagnostic including `Marshal.GetLastPInvokeError()` that names the interactive-session requirement (D-5.7 constraint #2 — the process must run in Session > 0; the launch mechanism in Plans 03/04 ensures this).
3. A read helper that, on every `WTSVirtualChannelRead`, scans forward for the first `{` byte and parses JSON from there — discarding any leading binary framing prefix (D-5.7 constraint #3; the empirically-observed 6-byte prefix from 04-03-SUMMARY). Wrap `JsonSerializer.Deserialize` in a try/catch scoped to `JsonException`, drop the malformed message, and keep the loop alive — never let an unhandled exception terminate `Main` (ASVS V5 / DoS mitigation, mirrors the Rust `serde_json::from_slice` drop-never-panic discipline).
4. Read the SDK's Version handshake FIRST (the SDK sends it unconditionally on channel creation — `RdpilotSensorProcessor::start()`), then write back this sensor's own `{version: 1, req_id: 0, type: "Version", payload: null}`.
5. Loop: for each inbound `type == "Ping"`, write `{version: 1, req_id: <same>, type: "Pong", payload: null}`; ignore any other type. `WTSVirtualChannelClose` on exit.

Add `sensor/.gitignore` (ignore `bin/`, `obj/`) and append a `sensor/bin/` + `sensor/obj/` ignore to the repo root `.gitignore`. Do NOT add COM/UIA usage — Version/Ping-only this phase (D-5.4).</action>

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-05-01 | Denial of Service | sensor Program.cs read loop | medium | mitigate | `JsonException`-scoped try/catch drops malformed/oversized inbound bytes and keeps `Main`'s loop alive — never an unhandled exception (ASVS V5, mirrors the Rust processor's drop-never-panic). |
| T-05-02 | Tampering | `[DllImport]` string marshalling under AOT | high | mitigate | Use `[LibraryImport]` source-generated marshalling exclusively (RESEARCH Pitfall 1); grep-gate forbids `DllImport`. |
| T-05-03 | Spoofing | Same-session process impersonating the DVC peer | low | accept | Unchanged Phase-4 accepted risk — DVC is unauthenticated by design on the single-tenant lab VM; not re-litigated (RESEARCH Security Domain). |
</threat_model>
