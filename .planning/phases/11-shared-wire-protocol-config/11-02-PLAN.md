<objective>
Create the `rdpilot-config` workspace crate: layered configuration resolution over a platform-config-dir TOML file, env vars, then flag/MCP-init overrides — with the highest-precedence layer deterministically winning. Its resolved-config type is an owned struct (never `rdpilot::ConnectionConfig`), and it never derives `Serialize`, so credentials cannot be wire-serialized by accident even before the `rdpilot-ipc` boundary.

Purpose: Delivers CONFIG-01 (deterministic layered precedence) and CONFIG-02 (discoverable, self-explanatory, platform-convention config file). Keeping the crate free of `rdpilot`/IronRDP (Decision 1) means the daemon (Phase 12) converts `ResolvedConfig -> rdpilot::ConnectionConfig` at startup, while thin CLI/MCP clients (Phase 13/14) can read config without linking the RDP stack.

Output: A buildable, tested `crates/rdpilot-config/` crate added as a workspace member, exporting `ResolvedConfig`, `ConfigError`, `config_file_path`, `resolve`/`apply_overrides`, and a `CONFIG_TEMPLATE` string asset.
</objective>

Binding resolved decisions from the phase discussion:

- **Decision 1 (dependency-free of `rdpilot`):** `rdpilot-config` MUST NOT depend on `rdpilot`. `ResolvedConfig` is its own owned struct, NOT `rdpilot::ConnectionConfig`. The `ResolvedConfig -> rdpilot::ConnectionConfig` conversion is a Phase 12 daemon-startup step, out of scope here.
- **Decision 2 (single config location; "gitignored" satisfied structurally):** Config lives ONLY at the platform config dir (D-27: `~/.config/rdpilot/config.toml` / `%APPDATA%\rdpilot\config.toml`). There is NO repo-local `.rdpilot.toml` layer. CONFIG-02's "gitignored" is satisfied because the file lives outside the repo tree. As a defensive no-cost measure, still add `config.toml` and `.rdpilot.toml` to the repo `.gitignore` (RESEARCH Open Question 3 recommendation).

Key vocabulary (D-27, one canonical spelling across file/env/flag/MCP-init): `host`, `port`, `username`, `password`, `domain`, `accept_invalid_certs` (the cert-bypass key). These are the `ResolvedConfig` fields.

Scope boundary: Phase 11 only READS config. No `config init` / file-WRITE path is in scope (that is a later CLI phase). Do NOT implement a writer here — but document in `paths.rs`/`resolved.rs` doc comments that whichever phase adds a writer must set `0600` permissions on Unix (RESEARCH Pitfall 4).
</scope_decisions>
