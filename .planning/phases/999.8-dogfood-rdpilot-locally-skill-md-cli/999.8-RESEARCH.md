## Summary

This phase has no new library integration — it packages and documents what already exists. All research effort went into (1) exhaustively enumerating the real `rdpilot` CLI verb surface from `crates/rdpilot-cli/src/cli.rs` so the SKILL.md reference section is accurate, (2) confirming the config schema/paths from `crates/rdpilot-config`, (3) confirming daemon auto-start/lifecycle mechanics, and (4) **empirically building and running both binaries on this exact box**, which surfaced a build-breaking environment gotcha not mentioned anywhere in CONTEXT.md: this repo's `rust-toolchain.toml` and `.cargo/config.toml` are pinned for the original ARM64-Windows dev machine (`stable-x86_64-pc-windows-gnu` toolchain, forced Windows-GNU cross-compile target with a Windows-only linker path). A plain `cargo build`/`cargo install` on this Linux box **fails outright** with either a toolchain-channel error or an `E0463 can't find crate for core` cross-compile error. The install script MUST explicitly override both the toolchain (`cargo +stable ...`) and the target (`--target x86_64-unknown-linux-gnu`, or a `rustc -vV`-detected host triple) to build natively. This is the single most important finding of this research — CONTEXT.md's own "Reusable Assets" note ("CLI builds natively on this Linux host: `cargo build --release -p rdpilot-cli`") is **not accurate as a bare command** on this exact machine's current git state; the corrected, verified command is documented below.

Everything else confirmed cleanly: the full CLI verb tree (18 verbs across `connect/list/disconnect`, `perceive` [screenshot/world-state/uia/window list/process list], `input` [click/scroll/drag/type/key/launch/foreground], and `put`/`get`), the exact D-28 8-code exit taxonomy, the config file's exact schema and platform path (`~/.config/rdpilot/config.toml`, already has a committed placeholder-only template at `crates/rdpilot-config/assets/config.toml.template` that can be copied verbatim rather than hand-authored), and the daemon's auto-start mechanism — which is **not** a `$PATH` lookup as CONTEXT.md's D-2 wording implies, but a **sibling-file** lookup (`current_exe().with_file_name("rdpilot-daemon")`). Both binaries must land in the exact same directory, which `cargo install --root ~/.cargo` naturally satisfies as long as both installs target the same `--root`.

For SKILL.md discovery format and the D-1/D-2 dual-location install, this machine already has a **live, working local precedent**: three other locally-authored skills (`crabbox`, `crabbox-browser-extensions`, `crabbox-browser-profile-persistence`) use the pattern "canonical copy under `~/.agents/skills/<name>/SKILL.md`, `~/.claude/skills/<name>` is a **symlink** to it." This is the recommended mechanism for rdpilot's install step too — it is simpler and less failure-prone than maintaining three independent copies (repo + 2 global copies), and matches this box's own established convention exactly.

**Primary recommendation:** Author `.claude/skills/rdpilot/SKILL.md` in the repo (source of truth, D-1). The install script (`scripts/install-local.sh`, plain POSIX/bash — `just` is present on this box but introducing a first justfile is a bigger structural commitment for zero portability gain) does four things in order: (1) `cargo +stable install --path crates/rdpilot-cli --target <host-triple> --root ~/.cargo` and the same for `crates/rdpilot-daemon`, both to the SAME `--root` so the sibling-binary auto-start lookup succeeds; (2) seed `~/.config/rdpilot/config.toml` (mode 0600) by copying `crates/rdpilot-config/assets/config.toml.template` verbatim if absent (idempotent — never overwrite an existing file); (3) place the real SKILL.md at `~/.agents/skills/rdpilot/SKILL.md` (copy from the repo path, since a symlink pointing back into a specific git worktree is more fragile than a copy for a "make it available on this box" install) and symlink `~/.claude/skills/rdpilot -> ~/.agents/skills/rdpilot`, mirroring the crabbox precedent; (4) run the D-8 smoke test (`rdpilot --version`, `rdpilot list`) and print the config path + next steps.

### Pattern 1: `cargo install` must explicitly override both toolchain and target on this box
**What:** `rust-toolchain.toml` pins `channel = "stable-x86_64-pc-windows-gnu"` and `.cargo/config.toml` pins `[build] target = "x86_64-pc-windows-gnu"` with a Windows-only MinGW linker path. These were set up for the project's original ARM64-Windows dev machine and are **still active** in the committed repo state as of this research.
**When to use:** Every `cargo build`/`cargo install`/`cargo test` invocation this install script runs.
**Verified failure mode (empirically reproduced on this exact box):**
```
$ cargo install --path crates/rdpilot-cli
error: target tuple in channel name 'stable-x86_64-pc-windows-gnu'
```
```
$ cargo +stable install --path crates/rdpilot-cli --root ~/.cargo
error[E0463]: can't find crate for `core`
  = note: the `x86_64-pc-windows-gnu` target may not be installed
```
**Verified working command (source: this research session, executed and confirmed producing working ELF binaries + a passing end-to-end smoke test):**
```bash
HOST_TRIPLE="$(rustc +stable -vV | awk '/^host:/ {print $2}')"   # x86_64-unknown-linux-gnu on this box
cargo +stable install --path crates/rdpilot-cli    --target "$HOST_TRIPLE" --root ~/.cargo
cargo +stable install --path crates/rdpilot-daemon --target "$HOST_TRIPLE" --root ~/.cargo
```
Detecting the host triple dynamically (rather than hardcoding `x86_64-unknown-linux-gnu`) keeps the script correct if this ever runs on a different architecture.

### Pattern 2: daemon auto-start is a sibling-file lookup, not a `$PATH` lookup
**What:** `crates/rdpilot-cli/src/connect.rs::open_stream()` resolves the daemon binary as:
```rust
// Source: crates/rdpilot-cli/src/connect.rs (verified, lines 31-37)
let daemon_exe = std::env::current_exe()?.with_file_name(DAEMON_BINARY_NAME); // "rdpilot-daemon"
connect_or_spawn(&socket, &daemon_exe).await
```
**When to use:** Governs where the install script must place both binaries.
**Why it matters:** CONTEXT.md's D-2 phrasing ("the daemon MUST be on PATH") is imprecise and could mislead an implementer into installing `rdpilot` and `rdpilot-daemon` to two different PATH-visible directories (e.g. one via `cargo install`'s default `~/.cargo/bin`, the other manually copied to `/usr/local/bin`) — that would silently break autostart even though both are technically "on PATH", because the lookup is `current_exe()`'s **own directory**, not a `$PATH` search. The fix is trivial (`cargo install --root ~/.cargo` for BOTH crates puts both binaries in `~/.cargo/bin/`) but the SKILL.md and install script comments should call this out explicitly so a future edit doesn't split the two binaries across directories.
**Verified:** empirically confirmed — installed both to the same `--root`, ran `rdpilot list` with no daemon running, watched it spawn `rdpilot-daemon` from that exact directory and bind the socket successfully.

### Pattern 3: `~/.agents/skills/<name>/` canonical + `~/.claude/skills/<name>` symlink (established local convention)
**What:** This box already has three skills (`crabbox`, `crabbox-browser-extensions`, `crabbox-browser-profile-persistence`) installed with the real file tree under `~/.agents/skills/<name>/` and `~/.claude/skills/<name>` as a **symlink** pointing at it (verified via `ls -la ~/.claude/skills/`).

### Anti-Patterns to Avoid
- **Hardcoding `target/release/rdpilot` as the build output path in the install script or SKILL.md:** wrong on this box today — the pinned `.cargo/config.toml` target means a bare `cargo build` produces `target/x86_64-pc-windows-gnu/release/rdpilot.exe` (a Windows PE binary) or fails outright, never `target/release/rdpilot`. Always use the explicit `--target <host-triple>` override shown in Pattern 1.
- **Installing the two binaries to different `--root` directories:** breaks the sibling-lookup autostart (Pattern 2) even though both would be "on PATH."
- **Re-authoring the config.toml template by hand:** `crates/rdpilot-config/assets/config.toml.template` already exists, is already placeholder-only (every key commented out), and is already unit-tested (`template_parses_into_resolved_config`, `template_documents_every_d27_key`) to parse to an all-default `ResolvedConfig` and document every key. Copy it verbatim.
- **Overwriting an existing `~/.config/rdpilot/config.toml` on re-run:** the install script must be idempotent/safe to re-run (a developer will re-run it after every `git pull`) — only seed the config file if it does not already exist, so a user's real credentials are never clobbered by a re-install.

## Config Schema and Location (source of truth for SKILL.md config section)

Source: `crates/rdpilot-config/{resolved.rs,paths.rs,resolve.rs}` and the already-committed `crates/rdpilot-config/assets/config.toml.template`.

**Location:** `directories::BaseDirs::config_dir()` + `rdpilot/config.toml` — resolves to `~/.config/rdpilot/config.toml` on Linux (verified: `cargo test -p rdpilot-config` passes on this box, including `config_file_path_matches_platform_convention`), `%APPDATA%\rdpilot\config.toml` on Windows. **Fields** (all optional at the file layer — `#[derive(Deserialize)]`, absent key → `None`/`false`, never a parse failure):
| Field | Type | Notes |
|-------|------|-------|
| `host` | `Option<String>` | required (via file/env/flag) before `connect` will run |
| `port` | `Option<u16>` | daemon applies a default when unset |
| `username` | `Option<String>` | required before `connect` |

| `share_root` | `Option<String>` | daemon-local file-transfer staging root; default `<data_dir>/rdpilot/transfer-staging` (`~/.local/share/rdpilot/transfer-staging` on Linux) if unset |

## Daemon Auto-Start / Lifecycle (source of truth for D-6/D-7 skill guidance)

Source: `crates/rdpilot-ipc/src/transport.rs`, `crates/rdpilot-daemon/src/lifecycle.rs`. **All of the following was empirically exercised on this box**, not just read from source.

- **Socket path:** `<XDG_RUNTIME_DIR>/rdpilot/daemon.sock` (falls back to `<cache_dir>/rdpilot` if no runtime dir resolvable). Verified: `/run/user/1000/rdpilot/daemon.sock`, parent dir mode `0700` created atomically (`DirBuilderExt::mode`, no TOCTOU window).
- **Auto-start:** `connect_or_spawn` tries a plain connect first; on failure, spawns the daemon binary **found as a sibling of the CLI's own `current_exe()`** (see Architecture Pattern 2 above — NOT a `$PATH` search), detached, then retries connect over a bounded backoff (`50, 100, 200, 400, 800` ms). Two racing clients both spawning is a benign, handled case (loser hits `AddrInUse`, exits silently).
- **Idle reap:** a `Live` session with no observed activity for `idle_timeout` (default **30 minutes**, override `RDPILOT_DAEMON_IDLE_TIMEOUT_MS`) is closed by the daemon automatically.
- **Empty-registry self-shutdown:** once the session registry is empty, the daemon waits `empty_grace` (default **30 seconds**, override `RDPILOT_DAEMON_EMPTY_GRACE_MS`) before exiting — an anti-thrash grace period so a rapid disconnect→reconnect doesn't pay a full daemon cold-start.
- **Poll interval:** both watchers re-scan every `reap_interval` (default **15 seconds**, override `RDPILOT_DAEMON_REAP_INTERVAL_MS`).
- **These are safety-net backstops, not the primary cleanup path (D-7):** the skill must instruct agents to explicitly `disconnect` when finished — 30 minutes of a live but idle in-daemon credential/session is a real, documented exposure window (the config's own `password` field is plaintext, D-06/D-14).
- **Session naming (D-6):** `SessionId` accepts any non-empty string (verified: `FromStr` only rejects the empty string, no charset restriction) — so a convention like `<agent>-<purpose>` (e.g. `claude-inspect-billing-app`) is a pure convention, not an enforced format. The skill should instruct agents to run `rdpilot list` before `connect` to check for a name collision, since `Connect` returns `DuplicateSession` (exit code 7) on a name clash.

## Common Pitfalls

### Pitfall 1: Bare `cargo build`/`cargo install` silently targets Windows on this box
**What goes wrong:** Following CONTEXT.md's own "Reusable Assets" note literally (`cargo build --release -p rdpilot-cli`) either errors immediately (toolchain-channel parse error) or, with `+stable` forced, fails to cross-compile (`E0463`, missing Windows-GNU std) — it never silently produces a working Linux binary.
**Why it happens:** `rust-toolchain.toml` + `.cargo/config.toml` were set up for the project's original ARM64-Windows dev machine and were never scoped out for this Linux dogfood box.
**How to avoid:** Always pass `+stable --target <host-triple>` explicitly, as verified in Architecture Pattern 1 above.
**Warning signs:** Any error mentioning `x86_64-pc-windows-gnu`, `target tuple in channel name`, or `E0463`.

### Pitfall 2: Splitting the two binaries across install directories breaks autostart silently
**What goes wrong:** If `rdpilot` and `rdpilot-daemon` end up in different (both PATH-visible) directories, `rdpilot list`/`connect` will fail with `DaemonUnreachable` (exit code 3) even though `which rdpilot-daemon` succeeds.
**Why it happens:** Autostart resolves the daemon path via `current_exe().with_file_name(...)`, not a `$PATH` search (Architecture Pattern 2).
**How to avoid:** Always `cargo install` both crates to the identical `--root` (e.g. always `~/.cargo`, never mix a manual `cp` to `/usr/local/bin` for one binary).
**Warning signs:** `rdpilot list` hangs for ~1.5s (the full backoff sequence) then fails with exit code 3.

### Pitfall 3: Re-running the install script clobbers a real credential file
**What goes wrong:** If the seed step unconditionally overwrites `~/.config/rdpilot/config.toml`, a developer's real host/username/password gets wiped on every re-install (e.g. after `git pull`).
**Why it happens:** Naive "always copy the template" logic.
**How to avoid:** Guard the seed step with an existence check — only copy the template if the destination file is absent.
**Warning signs:** A developer reports losing their configured target after re-running the install script.

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| World-readable seeded config.toml exposing a later-populated plaintext password to other local accounts | Information Disclosure | `chmod 600` immediately after creation (matches the crate's own doc comment obligation in `resolved.rs`) — never a post-hoc chmod with a TOCTOU window; create with restrictive mode or chmod before any content is written if a two-step create is unavoidable |
