  </behavior>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| racing clients → single daemon | Multiple clients may spawn a daemon simultaneously; exactly one must end up listening |
| accepted connection → serve loop | Each connection is authorized (peer-uid, Plan 04) before dispatch |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-12-18 | Spoofing / DoS | Double-spawn race producing two daemons on one socket | high | mitigate | Bind-as-mutex: the losing daemon hits AddrInUse and exits cleanly; no PID file |
| T-12-19 | Denial of Service | Idle sessions accumulating / daemon never shutting down (resource retention) | medium | mitigate | Idle reaper (config timeout) closes stale sessions via close(); empty_watcher self-exits after grace (D-31) |
| T-12-20 | Information Disclosure | Raw `Request` (Connect password) logged in the accept/serve loop | high | mitigate | Loop must not log raw requests; redaction obligation enforced (D-31) |
| T-12-21 | Elevation of Privilege | Unauthorized connection reaching dispatch | critical | mitigate | Accept loop routes through `accept_and_authorize` (peer-uid, Plan 04) before `serve_connection`; auth failure dropped, not served |
</threat_model>
